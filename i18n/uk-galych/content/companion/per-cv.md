## summary
Детектор на борту — то не «запустити YOLO», а вибір між класичними методами (колір, контури, маркери — дешево, передбачувано, крихко) і нейромережею (стійко, дорого, треба прискорення), а потім вимірювання: FPS на цільовому залізі, точність (precision/recall/mAP) на **своїх** даних, хибні спрацьовування та їхня ціна в контурі керування. Модуль проходить обидві гілки з кодом, показує запуск моделі на Jetson (TensorRT) і Pi (NCNN/ONNX Runtime/Coral) та вчить чесно оцінювати, шо ся вийшло.

## theory
### Класика: коли її вистачає
- **Маркери** (ArUco/AprilTag): відомий об'єкт із кодом → детекція + поза 6DoF із субпіксельною точністю, десятки FPS на Pi, стійкість до освітлення. Для точної посадки, калібрування, тестів контуру — найліпший вибір (ArduPilot precision landing вміє AprilTag через companion, `PLND_TYPE = 1` MAVLink `LANDING_TARGET`).
- **Колір + контури**: HSV-поріг → морфологія → `findContours` → фільтр за площею/формою. 2–5 мс на кадр. Ламає ся, як зміниться освітлення; пороги калібрувати на місці.
- **Фон/рух**: віднімання фону (`createBackgroundSubtractorMOG2`) — лише для нерухомої камери; з дрона — оптичний потік і компенсація руху, а то вже складно.
- **Шаблони/ознаки** (ORB + зіставлення): для відомого об'єкта; крихко до масштабу й повороту.

### Нейромережі: детекція
Однопрохідні детектори (сімейство YOLO, SSD, NanoDet) — вхід 320–640 px, вихід — бокси з класом і впевненістю, потім NMS. Факти для борту:
- **Розмір моделі**: nano/small (2–10 млн параметрів) — єдиний реальний варіант на Pi/Jetson Nano/Orin Nano; medium — Orin NX/AGX.
- **Прискорення**: Jetson — експорт у TensorRT (FP16/INT8, ×3–10 до PyTorch); Pi 4/5 — NCNN або ONNX Runtime на CPU (nano-модель 320 px: 5–15 fps на Pi 5), Coral USB (INT8-моделі) або Hailo-8L (Pi AI Kit, 13 TOPS) ци Hailo-8 (AI HAT+ 26 TOPS) — десятки fps; ARM-ноутбуки/міні-ПК із GPU — будь-який стек.
- **Донавчання** на своїх даних обов'язкове: попередньо навчена на COCO модель «бачить» людей і машини, але не твій маркер/об'єкт. 300–1000 розмічених кадрів із борту (різні висоти, освітлення, фон), аугментації, 50–100 епох на ПК/Colab; експорт в ONNX → TensorRT/NCNN.
- **Квантування** INT8 — ×2 за швидкістю, −1–3% mAP; калібрувальний набір зі своїх даних.

### Метрики, шо мають сенс
- **Precision** = TP/(TP+FP) — частка правильних серед знайдених; **Recall** = TP/(TP+FN) — частка знайдених серед справжніх; поріг упевненості посуває одне коштом другого (PR-крива).
- **mAP@0.5** — площа під PR за IoU ≥ 0.5; стандарт, але для борту важливіше: recall за фіксованої precision (ціна FP — хибний маневр!) і **затримка** повного циклу (захоплення → інференс → NMS → команда).
- Оцінювати на **відкладених** кадрах із борту, не на навчальних; окремо за умовами (висота, освітлення) — модель «у середньому 0.9» може дати 0.5 на заході сонця.
- **Аналіз FP**: класифікувати хибні спрацьовування (схожий об'єкт, тінь, край кадру, відблиск) — кожна група ся лікує по-своєму: дані, поріг, геометричний фільтр (розмір об'єкта за висотою польоту), часова фільтрація (об'єкт мусить ся появити в N кадрах підряд — трекер).

### Розібраний приклад: метрики з лічильників
Відкладений набір: 200 кадрів, на них 250 об'єктів. Детектор за порогу впевненості 0.5 видав 230 рамок: 210 збіглися з розміткою за IoU ≥ 0.5 (TP), 20 — хибні (FP), 40 об'єктів пропущено (FN).
- Precision = TP / (TP + FP) = 210/230 = **0.91** — із того, шо знайшли, 91 % правда.
- Recall = TP / (TP + FN) = 210/250 = **0.84** — із того, шо було, знайшли 84 %.
- IoU = площа перетину / площа об'єднання рамок; 0.5 — «збіглося», 0.75 — «збіглося точно».

Поріг 0.3 дає, скажімо, precision 0.80 і recall 0.93; поріг 0.7 — 0.96 і 0.70. Котрий вибрати — вирішує ціна помилки, а не краса числа: у пошуку людини пропуск дорожчий за хибну тривогу (поріг нижчий, хибні тривоги перевіряє оператор), в автоматичній дії по цілі навпаки (поріг вищий плюс підтвердження кількома кадрами).

### Трекер поверх детектора
Детектор на кожному кадрі — шумний і дорогий. Трекер (SORT/ByteTrack: Kalman + зіставлення за IoU) дає стабільні ID, згладжує, переживає пропуски й дає змогу детектувати на кожному 2–3-му кадрі. Для контуру керування команди ся беруть від трекера, а не від сирого детектора.

### Пайплайн на борту
Захоплення (потік, останній кадр) → препроцесинг (resize, letterbox, нормалізація — на GPU/апаратно, де ся дасть) → інференс → NMS → трекер → публікація (ROS 2 топік / MAVLink / ZeroMQ) з timestamp кадру. Профілювати кожну стадію (`time.perf_counter`); типові пропорції на Jetson Orin Nano для YOLO-nano 640: захоплення 3 мс, препроцес 2, інференс TensorRT FP16 8–12, постпроцес 2 → 15–20 мс, 50 fps теоретично, 30 із запасом.

## practice
### Крок 1. Класика
ArUco — детекція маркера з камери, виведення id і кутів, FPS. З OpenCV 4.7 API інший (старі `cv2.aruco.detectMarkers` зі статей гет не працюють):
```python
import cv2, time
dictionary = cv2.aruco.getPredefinedDictionary(cv2.aruco.DICT_4X4_50)
detector = cv2.aruco.ArucoDetector(dictionary, cv2.aruco.DetectorParameters())
cap = cv2.VideoCapture(0)
t0, n = time.perf_counter(), 0
while n < 300:
    ok, frame = cap.read()
    if not ok:
        break
    corners, ids, _ = detector.detectMarkers(cv2.cvtColor(frame, cv2.COLOR_BGR2GRAY))
    if ids is not None:
        c = corners[0][0]
        print(ids.ravel()[0], "centre px:", c.mean(axis=0).round(1))
    n += 1
print(f"{n / (time.perf_counter() - t0):.1f} FPS")
```
HSV-детектор кольорового об'єкта: пороги підібрано за гістограмою, площа/форма фільтрують; FPS і хибні спрацьовування, як ся міняє світло.

### Крок 2. Дані й донавчання
Зняти 300+ кадрів об'єкта з борту/з руки в різних умовах; розмітити (CVAT/LabelImg/Roboflow); навчити nano-модель (Ultralytics/NanoDet) на ПК; експорт ONNX. Відкладений набір — 20%.

### Крок 3. На борту
Jetson: ONNX → TensorRT FP16 (`trtexec`), інференс у Python; Pi: NCNN/ONNX Runtime або Coral/Hailo. Профіль за стадіями, FPS із камерою (не з файлу!).

### Крок 4. Оцінювання
Precision/recall/mAP на відкладеному наборі, за умовами; крива precision–recall за 5 порогами й вибраний поріг з обґрунтуванням ціною помилки (як у розібраному прикладі); FP класифіковано; трекер поверх (ByteTrack/SORT) — стабільність ID на відео.

### Як рахувати і шо записати
- **FPS — із камерою, а не з файлу:** захоплення, попередня обробка й інференс разом. Профіль за стадіями (мс на кадр) покаже, де вузьке місце. Часто то не нейромережа, а копіювання кадру та зміна розміру.
- **Precision і recall на відкладеному наборі.** Приклад: у відкладених кадрах 100 об'єктів, детектор знайшов 90 із них і ще 10 разів спрацював на порожньому місці. Precision = 90 / (90 + 10) = 0.90, recall = 90 / 100 = 0.90. Вищий поріг упевненості звичайно піднімає precision і знижує recall.
- **Вибір порогу через ціну помилки.** Як хибне спрацьовування відводить апарат за чужою ціллю, а пропуск означає лише повторний захід, бери поріг із високою precision, навіть ціною recall. Запиши криву за 5 порогами й вибрану точку з одним реченням обґрунтування.
- **Хибні спрацьовування за класами:** відблиски, тіні, схожі об'єкти, розмиття руху. Для кожного класу — приклад кадру й захід: дані в навчання, фільтр за розміром або формою, трекер із підтвердженням за кількома кадрами.
- **ArUco:** id маркера й кути стабільні за нерухомої камери. Як кути «скачуть», маркер малий у кадрі або камеру не відкалібровано (модуль «Камера»).

Лабораторна зараховує ся, коли модель запущено на борту з FPS, виміряним із камерою за стадіями, precision/recall пораховано на відкладеному наборі з вибраним порогом та обґрунтуванням, а хибні спрацьовування класифіковано із заходом для кожного класу.

## diagnostics
- **Симптом:** 30 fps на файлі, 8 fps із камери
  - Можлива причина: захоплення/конвертація на CPU, копії кадру.
  - Що зробити: профіль стадій, апаратний препроцес, нижча роздільна здатність.
- **Симптом:** mAP 0.9 на валідації, а в полі — не бачить
  - Можлива причина: валідація з того самого розподілу, шо й навчання; поле інше.
  - Що зробити: відкладені кадри з інших умов, дозібрати дані.
- **Симптом:** хибні спрацьовування на тінях/відблисках
  - Можлива причина: мало негативних прикладів.
  - Що зробити: додати «порожні» кадри з тінями в навчання, часова фільтрація.
- **Симптом:** після INT8 точність фест упала
  - Можлива причина: кепське калібрування квантування.
  - Що зробити: калібрувальний набір зі своїх даних, FP16 як компроміс.
- **Симптом:** ID об'єкта скаче
  - Можлива причина: нема трекера або слабке зіставлення.
  - Що зробити: ByteTrack, детекція на кожному кадрі для тестів.

## checklist
- Знаю, коли вистачає класики (маркери, колір), а коли треба мережа
- Донавчив nano-модель на своїх даних і експортував
- Модель запущено на борту з прискоренням, FPS виміряно з камери
- Precision/recall за умовами, поріг вибрано за ціною FP
- FP класифіковано, трекер згладжує детекції
