## summary
INAV Programming Framework (IPF) — спосіб додати апарату логіку без Lua і без companion: «якщо далі 100 м — підняти потужність VTX», «якщо напруга нижча за поріг — увімкнути RTH», «перемкнути канал за умовою». Логічні умови виконуються прямо в прошивці, працюють із телеметрією, режимами, точками місії та глобальними змінними. Модуль пояснює модель (умова = операція + два операнди), синтаксис CLI, GVAR і типові застосування, включно з порівнянням із Lua в ArduPilot.

## theory
### Модель
- **Logic Condition** — один рядок «коду»: операція над одним-двома операндами, з результатом true/false або числом.
- **Операнд** — число, канал RC, параметр польоту (відстань до дому, напруга, висота, швидкість), режим, інша умова, GVAR, точка місії.
- **Активатор** — інша умова, яка має бути true, щоб ця виконалася (−1 — завжди).
- **GVAR** — глобальні змінні, цілі від −32768 до 32767; їх можна читати, записувати, збільшувати й використовувати в міксері серв.
- **Programming PID** — чотири налаштовувані регулятори, вихід яких доступний як операнд.

### Синтаксис CLI
```
logic <rule> <enabled> <activatorId> <operation> <opA type> <opA value> <opB type> <opB value> <flags>
```

Типи операндів: 0 — значення, 1 — RC-канал, 2 — параметр польоту, 3 — режим, 4 — логічна умова, 5 — GVAR, 6 — Programming PID, 7 — точки місії. Операції: порівняння (дорівнює, більше, менше), логічні (AND, OR, NOT), арифметика, Set/Increase/Decrease GVAR, Override Throttle Scale, Override RC Channel, Set VTX power та інші.

### Приклад із документації: потужність VTX за віддаленням
Умова 0: «відстань до дому > 100 м». Умова 1 (активатор 0): «встановити потужність VTX = 3». Два правила — і передавач сам підвищує потужність, коли апарат далеко.

### Де IPF доречний
- автоматика на борту без другого комп'ютера: VTX, світло, PINIO, серви;
- умовні дії в місії через user actions;
- захисти: перемикання режиму за напругою або віддаленням;
- приладові завдання: GVAR як лічильники й стани.

### Проти Lua в ArduPilot
Lua — повноцінна мова з доступом до API автопілота, але потребує F7/H7 і пам'яті. IPF — набір правил без циклів і функцій, зате працює на F4 і налаштовується з конфігуратора. Складна логіка в IPF швидко стає нечитабельною; межа — десяток-два правил.

### Розібраний приклад: захист за напругою та віддаленням
Завдання: за напруги < 3.5 В/ел. і відстані > 300 м увімкнути RTH і підняти потужність VTX. Правила (`logic <rule> <enabled> <activator> <op> <A type> <A> <B type> <B> <flags>`):
- 0: `cell voltage < 350` (операнд польоту «середня напруга елемента, соті вольта» проти значення 350) — результат true/false;
- 1: `distance to home > 300` (метри);
- 2: AND з операндами «логічна умова 0» і «логічна умова 1» (тип операнда 4), без активатора → true, коли обидві;
- 3 (активатор 2): Override RC channel → канал режиму RTH у положення «увімк.» (RTH через перевизначення каналу);
- 4 (активатор 1): Set VTX power = 3.
Перевірка на столі без пропелерів: імітувати напругу (розряджена АКБ/регульований БЖ) і відстань (GVAR замість реального операнда на етапі тесту), дивитися статус правил на вкладці Programming конфігуратора. Правило-захист живе в прошивці, отже, його логіку треба задокументувати в паспорті апарата: за місяць «сам увімкнувся RTH» буде загадкою.

### Час і стан: EDGE, STICKY, DELAY, TIMER, DELTA
Правила без пам'яті дають «брязкіт»: напруга під навантаженням на секунду падає нижче порогу — і RTH вмикається від одного ривка газу. Для цього в IPF є операції з часом і пам'яттю:
- **DELAY** — true, тільки якщо умова A тримається безперервно N мс. Захист за напругою — завжди через DELAY (наприклад, 3000 мс), інакше захист спрацює від просідання на панчі.
- **STICKY** — засувка: вмикається за A і тримається, поки не прийде B (скидання). «Один раз спрацювало — RTH, поки пілот не скине тумблером».
- **EDGE** — true на N мс за фронтом A: одна подія від утримання тумблера.
- **TIMER** — періодично true/false: блимання світла, пульсація зумера.
- **DELTA** — зміна значення за короткий інтервал більша за поріг: «різкий спад висоти».

Переписаний захист: правило 0 → DELAY(3000) поверх «напруга < 350», потім STICKY з установленням за AND(0, 1) і скиданням за тумблером — і лише його результат активує перевизначення каналу.

### Налагодження
- Вкладка Programming показує стан і значення кожного правила наживо — це головний налагоджувач.
- GVAR можна вивести в OSD (елементи GVAR 0–3): видно стан автомата в польоті й на записі відео.
- `logic` і `gvar` у CLI друкують поточні правила — їхній дамп входить до `diff all`, тобто до резервної копії й у git (модуль «CI і версіонування конфігів»).

### Обмеження, на яких спотикаються
Правила виконуються у фіксованому порядку з частотою ~10 Гц; немає циклів, функцій, рядків; GVAR — цілі; перевизначення каналу (Override RC) конфліктує з реальним стіком — для режимів краще окремий «віртуальний» канал. Кількість правил фіксована прошивкою: 64 логічні умови, 8 GVAR, 4 Programming PID — однаково на F4 і H7. Якщо логіка потребує «станів» та історії — це вже companion.

## practice
### Крок 1. Перша пара правил у конфігураторі
Вкладка Programming: правило 0 — `Flight > Home distance (m)` більше `100`; правило 1 — активатор 0, операція `Set VTX Power`, значення 3. Зберегти, перевірити вкладку: стан умов показується наживо.

### Крок 2. Те саме в CLI
```
logic 0 1 -1 2 2 <home_distance_operand_id> 0 100 0
logic 1 1 0  <set_vtx_power_op_id> 0 3 0 0 0
save
```

Номери операцій і операндів — з таблиць у документації Programming Framework для своєї версії: вони змінюються між релізами, тому в модулі не зашиті.

### Крок 3. GVAR як стан
Правило: за спрацюванням тумблера збільшити GVAR 1 на 1; інше правило — якщо GVAR 1 парна, увімкнути світло, інакше вимкнути. Це скінченний автомат на двох рядках.

### Крок 4. Таблиця істинності до польоту
Для захисту з розібраного прикладу виписати всі комбінації входів і очікуваний вихід, потім перевірити кожен рядок на столі (без пропелерів), підміняючи реальні операнди на GVAR, які змінюються тумблером:

| Напруга < 3.5 В ≥ 3 с | Дім > 300 м | Засувка до цього | Очікувано |
|---|---|---|---|
| ні | ні | ні | нічого |
| так | ні | ні | нічого (близько — пілот сам) |
| ні | так | ні | нічого |
| так | так | ні | RTH + потужність VTX 3, засувка встановлюється |
| ні | ні | так | RTH тримається до скидання тумблером |

Рядок, який поводиться не так, — помилка в правилах, знайдена на столі, а не в полі.

### Лабораторна
Зібрати захист: якщо напруга нижча за поріг довше 3 с (DELAY) **і** відстань більша за 50 м — заклацнути засувку (STICKY) і перевизначити канал режиму в положення RTH (`Override RC Channel`). Пройти таблицю істинності на столі, перевірити в SITL INAV, потім у полі на малому віддаленні. Здати: дамп `logic`/`gvar`, заповнену таблицю, відео OSD зі станом GVAR.

## diagnostics
- **Симптом:** правило не спрацьовує
  - Можлива причина: активатор false, неправильний тип операнда (GVAR «значення 1» проти «GVAR 1»).
  - Що зробити: дивитися живий стан у вкладці Programming, перевірити типи.
- **Симптом:** Set GVAR пише не в ту змінну
  - Можлива причина: в операнді A вказано «Global Variable 1» замість «Value 1».
  - Що зробити: індекс GVAR задається як Value.
- **Симптом:** після оновлення INAV правила зламалися
  - Можлива причина: змінилися номери операцій/операндів.
  - Що зробити: звірити з таблицями версії, перезібрати правила.
- **Симптом:** логіка стала нечитабельною
  - Можлива причина: забагато правил для IPF.
  - Що зробити: спростити або перейти на Lua/ArduPilot.
