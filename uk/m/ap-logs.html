Логи ArduPilot: розбір польоту

L3 — Спеціалістчитання 30 хвнавчання ~3 годArduPilot 4.5+ОПАНОВАНО

ArduPilot пише на SD-карту бінарний лог DataFlash (.bin) із сотнями типів повідомлень: орієнтація, висота, мотори, батарея, EKF, помилки. Це чорна скринька, яка відповідає на питання «чому» після будь-якого дивного польоту. Модуль дає порядок розбору — від вібрацій до помилок — з конкретними іменами повідомлень і полів, порогами з документації та скриптом на Python для власних графіків.

Після модуля ти вмієш
  • знайти вібрації, просідання живлення, відмову сенсора в DataFlash

Перед цим модулем: EKF і навігація

Теорія

Два види логів

  • DataFlash (.bin) — на борту, висока частота, усе підряд. Основний інструмент.
  • Telemetry log (.tlog) — те, що бачила GCS по радіо. Рідше й з дірками, але є навіть тоді, коли SD-карта згоріла разом з апаратом.

Параметр LOG_BITMASK задає, що писати; LOG_DISARMED вмикає запис до арму (корисно для розбору pre-arm проблем).

Повідомлення, з яких починають

  • VIBE — вібрації: VibeX, VibeY, VibeZ (м/с²) і Clip — лічильник насичення акселерометра. Нижче 30 нормально, вище 60 майже напевно проблеми з висотою та позицією. Кліпінг має бути нульовим.
  • ATT — DesRoll проти Roll, DesPitch проти Pitch: наскільки апарат встигає за бажаним. Різке розходження — механічна проблема або брак тяги.
  • CTUN — керування висотою: ThO (вихід газу), ThH (оцінка газу зависання), DAlt/Alt (бажана й фактична висота), BAlt (баро).
  • BAT — Volt, Curr, CurrTot, Res (оцінка внутрішнього опору). Просідання під струмом і реальна витрата.
  • RCIN — канали з пульта C1…C14: що робив пілот.
  • MODE — зміна режимів і причина Rsn.
  • ERR — помилки: Subsys і ECode. Наприклад, підсистема 2 (радіо) з кодом 2 — немає кадрів приймача дві секунди; 11 — GPS-глітч; 16 — погана варіація EKF; 17 — EKF-failsafe; 29 — компенсація вібрацій.
  • MSG — текстові повідомлення, зокрема pre-arm.
  • GPS — NSats, HDop: HDOP нижче 1.5 добре, вище 2.0 підозріло; менше 12 супутників — погано.
  • XKF1…XKF4 — нутрощі EKF3 по ядрах: оцінки та варіації (XKF4: SV, SP, SH, SM — швидкість, позиція, висота, компас).
  • POWR — VCC плати: коливання понад 0.1–0.15 В натякають на проблеми живлення.

Порядок розбору

  1. Чи обривається лог? Лог, який закінчується в повітрі, — втрата живлення або перезавантаження.
  2. Вібрації (VIBE). Усе інше безглузде, поки вони високі.
  3. Помилки (ERR, MSG): що й коли спрацювало.
  4. Режими (MODE): хто змінював режим — пілот чи failsafe.
  5. Керування (ATT, CTUN): чи встигав апарат за командами.
  6. Живлення (BAT, POWR): просідання та їх збіг із подіями.
  7. Навігація (GPS, XKF4): якість позиції й варіації в момент проблеми.

Інструменти

Mission Planner (Review a Log), MAVExplorer з пакета MAVProxy (графіки за іменами полів, наприклад graph ATT.Roll ATT.DesRoll), UAV Log Viewer у браузері. Для автоматизації — pymavlink.DFReader: читає .bin напряму в Python.

Розібраний приклад: розбір «просідання висоти на 3 м у Loiter»

  1. VIBE.VibeZ 12 м/с², Clip 0 → не вібрації.
  2. ERR/MSG: немає.
  3. CTUN: DAlt 20 м стала, Alt провалюється до 17 м, BAlt одночасно → реальне просідання, не оцінка.
  4. CTUN.ThO у момент — 0.78 (до — 0.42), BAT.Volt 21.1 → 18.9 В, BAT.Curr 60 → 95 А: газ уперся в стелю на просілій АКБ.
  5. RCIN.C3 — пілот газ не чіпав; MODE без змін.

Висновок: брак тяги при просіданні напруги на старій АКБ (BAT.Res 0.09 Ом — високо): АКБ на заміну, MOT_BAT_VOLT_MIN/MAX для компенсації, поріг BATT_LOW_VOLT вище. Метод важливіший за висновок: кожен крок — конкретне поле.

Python для власних метрик (pymavlink)

from pymavlink import mavutil
import pandas as pd
def df_of(log, msg):
    m = mavutil.mavlink_connection(log); rows = []
    while (x := m.recv_match(type=msg, blocking=False)) is not None: rows.append(x.to_dict())
    return pd.DataFrame(rows)
att = df_of("flight.bin", "ATT")
err = (att.DesRoll - att.Roll).abs()
print("roll tracking RMS deg:", err.pow(2).mean() ** 0.5, "p99:", err.quantile(0.99))
vibe = df_of("flight.bin", "VIBE"); print("VibeZ p95:", vibe.VibeZ.quantile(0.95), "clips:", vibe.Clip.max())

mavlogdump.py --types ATT,VIBE --format csv flight.bin — швидке вивантаження в CSV без коду; MAVExplorer: graph ATT.Roll ATT.DesRoll, fft для спектрів батч-семплінгу (ISBH/ISBD), map для траєкторії. Метрики перехідного процесу та спектри — модуль «Python для даних».

Що писати в LOG_BITMASK

За замовчуванням достатньо для розбору польоту; для налаштування додати PID (повідомлення PIDR/PIDP/PIDY з P/I/D/FF по осях) і IMU_RAW/батч-семплінг (INS_LOG_BAT_MASK) на час налаштування фільтрів — лог зростає в рази, після — вимкнути. LOG_FILE_DSRMROT — новий файл при кожному дизармі; LOG_DISARMED = 1 — для наземних вимірювань (шум, GPS), потім вимкнути, інакше SD забивається.

Практика

Скрипт: вібрації та кліпінг за логом

import sys
from pymavlink import DFReader

log = DFReader.DFReader_binary(sys.argv[1])
vibe = {"VibeX": [], "VibeY": [], "VibeZ": []}
clip_max = 0
errors = []
while True:
    m = log.recv_msg()
    if m is None:
        break
    t = m.get_type()
    if t == "VIBE" and m.IMU == 0:
        for k in vibe:
            vibe[k].append(getattr(m, k))
        clip_max = max(clip_max, m.Clip)
    elif t == "ERR":
        errors.append((m.TimeUS / 1e6, m.Subsys, m.ECode))

for k, v in vibe.items():
    v = sorted(v)
    print(f"{k}: median {v[len(v)//2]:.1f}  p95 {v[int(len(v)*0.95)]:.1f} m/s/s")
print("accel clipping events:", clip_max)
for t, sub, code in errors:
    print(f"ERR at {t:7.1f}s  subsys={sub} ecode={code}")

Запуск: python vibe_report.py 00000012.BIN. Медіана вище 30 або ненульовий кліпінг — спершу механіка, потім усе інше.

Лабораторна

  1. Зроби в SITL політ із місією та відмовою мотора за тумблером.
  2. Завантаж лог (у SITL — папка logs/).
  3. Знайди момент відмови за RCIN (тумблер) і подивись, як розійшлися DesRoll/Roll і зросли виходи моторів (RCOU).
  4. Напиши звіт на п'ять рядків: що сталося, коли, як апарат упорався, які параметри варто змінити.

Реальний лог

Повтори те саме з логом реального зависання: вібрації, газ зависання (CTUN.ThH), просідання батареї. Збережи лог і звіт у папку дрона з датою.

Як влаштувати відмову мотора в SITL

Відмова задається параметрами симулятора: SIM_ENGINE_FAIL — маска моторів (біт 0 — вихід 1), SIM_ENGINE_MUL — множник їхньої тяги. На квадрокоптері повна відмова (SIM_ENGINE_MUL = 0) означає падіння, тому для навчального розбору бери часткову відмову (0.5–0.6) або раму hexa/octa, де повну відмову одного мотора можна пережити. Момент відмови в логу видно за записом PARM з новим значенням параметра або за тумблером у RCIN, якщо відмову повішено на канал пульта.

Що має вийти і що записати

  • Скрипт. У SITL вібрації малі (одиниці м/с²), і кліпінгу немає — механіки немає. На реальному апараті медіана нижче 30 м/с² і нульовий кліпінг: лише тоді розбирати решту. Запиши медіану та p95 по трьох осях.
  • ERR. Кожен запис розшифруй за таблицею підсистем із теорії: час, підсистема, код, що це означає.
  • Відмова. За частки секунди після неї розходяться ATT.DesRoll і ATT.Roll, а виходи моторів у RCOU роз'їжджаються: решта моторів працює із запасом, той, що відмовив, іде в максимум, намагаючись дати тягу. Запиши час до стабілізації та максимальне відхилення по крену.
  • Звіт на п'ять рядків, приклад: «12.3 с — відмова мотора 1 (×0.6). Крен відхилився до 14°, стабілізувався за 1.2 с. Виходи решти моторів зросли до 75 %, запас тяги є. Вібрації в нормі (медіана 4 м/с²), кліпінгу немає. Рекомендація: для цієї маси запас достатній, змінювати не потрібно.»
  • Реальний лог. Газ зависання CTUN.ThH порівняй з MOT_THST_HOVER; просідання батареї під газом видно в BAT.

Лабораторну зараховано, коли скрипт на DFReader виводить медіану VIBE і кліпінг, усі ERR розшифровано, момент відмови знайдено за PARM/RCIN з реакцією в ATT і RCOU, а звіт на п'ять рядків збережено поруч із логом.

Діагностика

Симптом: лог обривається в повітрі

  • Можлива причина: втрата живлення плати.
  • Що зробити: POWR.VCC перед обривом, паяння силових роз'ємів, BEC.

Симптом: VIBE високі, Clip зростає

  • Можлива причина: дисбаланс пропелерів/моторів, жорстке кріплення FC.
  • Що зробити: балансування, демпфери, перевірка рами — до будь-яких фільтрів.

Симптом: DesRoll і Roll розходяться, один мотор на максимумі в RCOU

  • Можлива причина: відмова або слабкість мотора/ESC, перевантаження.
  • Що зробити: перевірити мотор, пропелер, ESC; порівняти виходи моторів на зависанні.

Симптом: ERR 16/17 перед аварією

  • Можлива причина: погані варіації EKF — компас, GPS або вібрації.
  • Що зробити: XKF4 у той момент, причина — за попереднім модулем.
