UART, I2C, SPI, CAN на рівні сигналів і драйверів

L3 — Спеціалістчитання 40 хвнавчання ~3 годлюбая прошивкаОПАНОВАНО

Модуль «Підключення периферії» вчив підключати готове; цей — робити своє: як виглядають біти на лінії, навіщо стартовий біт і ACK, звідки беруться помилки кадру та NACK, як рахуються таймінги й обмежується довжина шини, і як пишеться драйвер датчика з нуля (I2C-барометр/IMU на ESP32: регістри, читання блоком, обробка помилок, таймаути). Завершується DroneCAN: кадри CAN 2.0, арбітраж, node ID, навіщо це великим апаратам і як виглядає пакет DroneCAN в аналізаторі.

Після модуля ти вмієш
  • пояснити таймінги, адресацію, pull-up, швидкість і помилки кожної шини
  • написати драйвер I2C-датчика на ESP32
  • розуміти DroneCAN і навіщо він на великих апаратах

Перед цим модулем: Embedded: переривання, таймери, DMA, RTOS, Вимірювання: мультиметр, осцилограф, логічний аналізатор

Теорія

UART

Асинхронний: немає тактової лінії, обидві сторони знають швидкість. Кадр: стартовий біт (0), 5–9 біт даних (LSB першим), опційно парність, 1–2 стопових (1). 8N1 на 115200 → 10 біт на байт → 11 520 байт/с. Приймач семплює в середині біта (зазвичай ×16 передискретизація); похибка швидкості до ~3–5% допустима, більша — framing error. Помилки: framing (стоп-біт не 1 — неправильна швидкість/інверсія), overrun (не встигли забрати байт — потрібен DMA/переривання), noise. Інверсія (SBUS): рівні перевернуті, idle = 0. Рівні 3.3 В TTL; RS-232/RS-485 — інші рівні/диф. пара (довгі лінії).

Драйвер: кільцевий буфер прийому за перериванням/DMA, парсер кадрів протоколу (CRSF: [адрес][длина][тип][payload][CRC8 0xD5]; MAVLink: magic 0xFD, довжина, seq, sysid/compid, msgid, CRC16 з CRC_EXTRA), таймаут між байтами для ресинхронізації.

I2C

Синхронний, дві лінії open-drain з підтяжками: SCL, SDA. Майстер генерує такт; транзакція: START (SDA↓ при SCL=1) → 7-біт адреса + біт R/W → ACK від веденого (SDA↓ на 9-му такті) → байти даних з ACK/NACK → STOP. Читання регістра: START, адреса+W, номер регістра, повторний START, адреса+R, дані, NACK останнього, STOP. Швидкості 100/400 кГц (fast), 1 МГц (fast-plus). Обмеження: ємність шини ≤ 400 пФ → дроти до ~30–50 см, підтяжки 2.2–4.7 кОм (менше — крутіші фронти, більший струм). Помилки: NACK на адресу (немає пристрою/адреса/живлення), NACK на дані, зависла шина (ведений тримає SDA=0 після збою майстра — лікується 9 тактами SCL вручну, «bus recovery»), clock stretching (ведений тягне SCL — майстер має вміти чекати; у деяких МК/датчиків проблеми).

SPI

Синхронний, повний дуплекс: SCLK, MOSI, MISO, CS (по лінії на пристрій). Немає адрес і ACK: майстер опускає CS, видає такти, кожен такт зсуває біт в обидва боки. Режими CPOL/CPHA (0–3) — полярність/фаза такту, мають збігатися з даташитом (ICM42688 — mode 0 або 3). Швидкості до десятків МГц (гіроскоп 8–24 МГц, flash 50+). Читання регістра: байт адреси з бітом R (часто старший біт = 1), потім N байт сміття на MOSI — дані на MISO. Burst-читання 14 байт IMU за одну транзакцію — так роблять усі прошивки. Помилок «протоколу» немає — перевірка цілісності лише за змістом (регістр WHO_AM_I, значення в діапазоні). Короткі доріжки: SPI назовні плати майже не виводять.

CAN і DroneCAN

CAN 2.0: диференціальна пара CAN_H/CAN_L, термінатори 120 Ом з обох кінців, до 1 Мбіт/с (до 40 м при 1 Мбіт, довше — повільніше). Кадр: ідентифікатор 11 або 29 біт (розширений), DLC, до 8 байт даних, CRC15, ACK від будь-якого приймача. Арбітраж: усі передають одночасно, домінантний 0 перемагає рецесивну 1 — менший ID виграє без втрати часу; пріоритет закладено в ID. Контролер CAN у МК приймає/надсилає кадри апаратно, фільтрує за ID; помилки рахуються (error passive/bus-off при 256 помилках — вузол відключається).

DroneCAN (колишній UAVCAN v0): поверх CAN — 29-бітний ID з пріоритетом, типом повідомлення та node ID джерела (1–127), багатокадрові повідомлення з транспортним CRC і toggle-бітом, динамічний розподіл node ID (DNA), стандартні типи: uavcan.equipment.gnss.Fix2, ahrs.MagneticFieldStrength2, esc.RawCommand/Status, power.BatteryInfo, range_sensor.Measurement. Навіщо на великих апаратах: одна вита пара на всі пристрої, завадостійкість диф. пари та CRC, телеметрія від кожного ESC, гаряча заміна вузлів, довгі лінії (крило 2 м), без «один UART — один пристрій». Інструмент: DroneCAN GUI Tool (SLCAN-адаптер або польотник як міст CAN_SLCAN_CPORT) — видно вузли, параметри вузлів, повідомлення.

Драйвер: що має бути

  1. Ініціалізація шини та перевірка пристрою (WHO_AM_I/chip id).
  2. Конфігурація (регістри): діапазон, частота, фільтри.
  3. Читання блоком з таймаутом; повернення помилки, а не зависання.
  4. Перетворення сирих одиниць на фізичні (LSB → °/с, Па).
  5. Обробка помилок: лічильники, повторна ініціалізація після N помилок поспіль, bus recovery для I2C.
  6. Потокобезпечність: м'ютекс на шину, якщо пристроїв кілька.

Практика

Крок 1. Драйвер I2C-датчика (ESP32, ESP-IDF; приклад на legacy-API driver/i2c.h, який оголошено end-of-life з ESP-IDF v6.0 — у нових проєктах driver/i2c_master.h: i2c_master_transmit_receive/i2c_master_transmit)

Приклад для BMP280 (адреса 0x76/0x77, chip id 0x58 у регістрі 0xD0):

static esp_err_t rd(uint8_t reg, uint8_t *buf, size_t n) {       // repeated-START read, 50 ms timeout
  return i2c_master_write_read_device(I2C_NUM_0, ADDR, &reg, 1, buf, n, pdMS_TO_TICKS(50));
}
static esp_err_t wr(uint8_t reg, uint8_t val) {
  uint8_t b[2] = { reg, val };
  return i2c_master_write_to_device(I2C_NUM_0, ADDR, b, 2, pdMS_TO_TICKS(50));
}
esp_err_t bmp280_init(void) {
  uint8_t id; ESP_RETURN_ON_ERROR(rd(0xD0, &id, 1), TAG, "no response");
  if (id != 0x58) return ESP_ERR_NOT_FOUND;
  ESP_RETURN_ON_ERROR(rd(0x88, calib, 24), TAG, "calib");         // dig_T1..dig_P9
  return wr(0xF4, 0x57);                                            // osrs_t x2, osrs_p x16, normal mode
}
esp_err_t bmp280_read(float *temp_c, float *press_pa) {
  uint8_t d[6]; esp_err_t e = rd(0xF7, d, 6); if (e != ESP_OK) { errors++; return e; }
  int32_t adc_p = (d[0] << 12) | (d[1] << 4) | (d[2] >> 4), adc_t = (d[3] << 12) | (d[4] << 4) | (d[5] >> 4);
  /* compensation formulas from the datasheet (bmp280_compensate_T/P) */ ...
  return ESP_OK;
}

Читати 50 Гц, виводити; після 5 помилок поспіль — переініціалізація з логом.

Крок 2. Аналізатор

Зняти транзакцію: START, адреса+W, 0xF7, повторний START, адреса+R, 6 байт, NACK, STOP. Зіставити байти з виводом. Записати тривалість транзакції при 400 кГц (очікувано ~0.2 мс).

Крок 3. Зламати шину

Від'єднати SDA на ходу → NACK/таймаут, лічильник помилок, переініціалізація; замкнути SDA на землю на секунду → зависла шина; реалізувати recovery (9 тактів SCL у GPIO-режимі) і показати відновлення.

Крок 4. DroneCAN (якщо є вузол)

DroneCAN GUI Tool через SLCAN-міст польотника: побачити node ID, GetNodeInfo, повідомлення GPS/компаса; зняти кадр CAN аналізатором і розібрати 29-бітний ID на пріоритет/тип/джерело.

Що має вийти і що записати

  • Читання датчика. Регістр 0xD0 BMP280 повертає chip id 0x58 — перша перевірка, що драйвер говорить із тим пристроєм. Якщо приходить 0x60, це BME280 (у нього є й вологість). Тиск і температура після компенсації за калібрувальними коефіцієнтами — правдоподібні: близько 1000 гПа і кімнатна температура. Підніми плату на метр — тиск упаде приблизно на 0.12 гПа.
  • Тривалість транзакції. Читання 6 байт із повторним стартом на 400 кГц — близько 85 тактів шини (адреси, регістр, дані, ACK) × 2.5 мкс ≈ 0.21 мс. Порівняй з аналізатором: помітно довше — отже, драйвер робить паузи між байтами або на лінії слабкі підтяжки (пологі фронти).
  • Помилки. Від'єднана SDA дає NACK або таймаут, лічильник помилок зростає, після п'яти поспіль — переініціалізація із записом у лог. SDA, притиснута до землі, вішає шину. Дев'ять тактів SCL у режимі GPIO звільняють ведений пристрій, і читання відновлюється. Запиши час від збою до відновлення.
  • CAN. 29-бітний ID кадру DroneCAN розібрано на пріоритет, тип повідомлення та номер вузла-відправника, і номер збігається з тим, що показує DroneCAN GUI Tool.

Лабораторну зараховано, коли I²C-датчик прочитано власним драйвером із перевіркою chip id, шину знято аналізатором із тривалістю транзакції, а помилку на шині відтворено й оброблено з відновленням.

Діагностика

Симптом: UART приймає сміття

  • Можлива причина: швидкість/інверсія/немає спільної землі; overrun без DMA.
  • Що зробити: перевірити аналізатором, DMA-прийом, лічильники framing/overrun.

Симптом: I2C-транзакція «висить»

  • Можлива причина: ведений тримає SDA; clock stretching без підтримки.
  • Що зробити: таймаути в драйвері, bus recovery, знизити до 100 кГц.

Симптом: SPI повертає 0xFF/0x00

  • Можлива причина: CS не опускається, режим CPOL/CPHA, занадто швидко.
  • Що зробити: осцилограф на CS/SCLK, режим за даташитом, тест WHO_AM_I.

Симптом: CAN-вузол іде в bus-off

  • Можлива причина: немає термінаторів, різна швидкість, переплутано H/L.
  • Що зробити: 120 Ом з обох кінців, одна швидкість, лічильники помилок.

Симптом: датчик працює на столі, але не на борту

  • Можлива причина: завади на I2C від силових ліній, довжина дротів.
  • Що зробити: коротше/виті/екран, SPI або CAN замість I2C.
