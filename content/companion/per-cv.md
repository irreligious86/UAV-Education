## summary
Детектор на борту — это не «запустить YOLO», а выбор между классическими методами (цвет, контуры, маркеры — дёшево, предсказуемо, хрупко) и нейросетью (устойчиво, дорого, нужно ускорение), затем измерение: FPS на целевом железе, точность (precision/recall/mAP) на **своих** данных, ложные срабатывания и их цена в контуре управления. Модуль проходит обе ветки с кодом, показывает запуск модели на Jetson (TensorRT) и Pi (NCNN/ONNX Runtime/Coral), и учит оценивать результат честно. Лабораторная: модель на борту, FPS и точность измерены, ложные срабатывания проанализированы.

## theory
### Классика: когда её хватает
- **Маркеры** (ArUco/AprilTag): известный объект с кодом → детекция + поза 6DoF с субпиксельной точностью, десятки FPS на Pi, устойчиво к освещению. Для точной посадки, калибровки, тестов контура — лучший выбор (ArduPilot precision landing умеет AprilTag через companion, `PLND_TYPE = 1` MAVLink `LANDING_TARGET`).
- **Цвет + контуры**: HSV-порог → морфология → `findContours` → фильтр по площади/форме. 2–5 мс на кадр. Ломается при смене освещения; калибровка порогов на месте.
- **Фон/движение**: вычитание фона (`createBackgroundSubtractorMOG2`) — только для неподвижной камеры; с дрона — оптический поток и компенсация движения, сложно.
- **Шаблоны/признаки** (ORB + сопоставление): для известного объекта; хрупко к масштабу и повороту.

### Нейросети: детекция
Однопроходные детекторы (семейство YOLO, SSD, NanoDet) — вход 320–640 px, выход — боксы с классом и уверенностью, затем NMS. Факты для борта:
- **Размер модели**: nano/small (2–10 млн параметров) — единственный реальный вариант на Pi/Jetson Nano/Orin Nano; medium — Orin NX/AGX.
- **Ускорение**: Jetson — экспорт в TensorRT (FP16/INT8, ×3–10 к PyTorch); Pi 4/5 — NCNN или ONNX Runtime на CPU (nano-модель 320 px: 5–15 fps на Pi 5), Coral USB (INT8-модели) или Hailo-8 (Pi AI Kit) — десятки fps; ARM-ноутбуки/мини-ПК с GPU — любой стек.
- **Дообучение** на своих данных обязательно: предобученная на COCO модель «видит» людей и машины, но не твой маркер/объект. 300–1000 размеченных кадров с борта (разные высоты, освещение, фон), аугментации, 50–100 эпох на ПК/Colab; экспорт в ONNX → TensorRT/NCNN.
- **Квантование** INT8 — ×2 по скорости, −1–3% mAP; калибровочный набор из своих данных.

### Метрики, которые имеют смысл
- **Precision** = TP/(TP+FP) — доля правильных среди найденных; **Recall** = TP/(TP+FN) — доля найденных среди истинных; порог уверенности двигает одно за счёт другого (PR-кривая).
- **mAP@0.5** — площадь под PR при IoU ≥ 0.5; стандарт, но для борта важнее: recall при фиксированной precision (цена FP — ложный манёвр!) и **задержка** полного цикла (захват → инференс → NMS → команда).
- Оценивать на **отложенных** кадрах с борта, не на обучающих; отдельно по условиям (высота, освещение) — модель «в среднем 0.9» может давать 0.5 на закате.
- **FP анализ**: классифицировать ложные срабатывания (похожий объект, тень, край кадра, блик) — каждая группа лечится по-своему: данные, порог, геометрический фильтр (размер объекта по высоте полёта), временная фильтрация (объект должен появиться в N кадрах подряд — трекер).

### Трекер поверх детектора
Детектор на каждом кадре — шумный и дорогой. Трекер (SORT/ByteTrack: Kalman + сопоставление по IoU) даёт стабильные ID, сглаживает, переживает пропуски и позволяет детектировать на каждом 2–3-м кадре. Для контура управления команды берутся от трекера, не от сырого детектора.

### Пайплайн на борту
Захват (поток, последний кадр) → препроцессинг (resize, letterbox, нормализация — на GPU/аппаратно, где возможно) → инференс → NMS → трекер → публикация (ROS 2 топик / MAVLink / ZeroMQ) с timestamp кадра. Профилировать каждую стадию (`time.perf_counter`); типичные пропорции на Jetson Orin Nano для YOLO-nano 640: захват 3 мс, препроцесс 2, инференс TensorRT FP16 8–12, постпроцесс 2 → 15–20 мс, 50 fps теоретически, 30 с запасом.

## practice
### Шаг 1. Классика
ArUco: `cv2.aruco` — детекция маркера с камеры, вывод id и углов, FPS. HSV-детектор цветного объекта: пороги подобраны по гистограмме, площадь/форма фильтруют; FPS и ложные срабатывания при смене света.

### Шаг 2. Данные и дообучение
Снять 300+ кадров с борта/с руки объекта в разных условиях; разметить (CVAT/LabelImg/Roboflow); обучить nano-модель (Ultralytics/NanoDet) на ПК; экспорт ONNX. Отложенный набор — 20%.

### Шаг 3. На борту
Jetson: ONNX → TensorRT FP16 (`trtexec`), инференс в Python; Pi: NCNN/ONNX Runtime или Coral/Hailo. Профиль по стадиям, FPS с камерой (не с файла!).

### Шаг 4. Оценка
Precision/recall/mAP на отложенном наборе, по условиям; порог выбран по цене FP; FP классифицированы; трекер поверх (ByteTrack/SORT) — стабильность ID на видео. Лабораторная: модель на борту, FPS и точность измерены, ложные срабатывания проанализированы.

## diagnostics
- **Симптом:** 30 fps на файле, 8 fps с камеры
  - Возможная причина: захват/конверсия на CPU, копии кадра.
  - Что сделать: профиль стадий, аппаратный препроцесс, нижнее разрешение.
- **Симптом:** mAP 0.9 на валидации, в поле — не видит
  - Возможная причина: валидация из того же распределения, что обучение; поле другое.
  - Что сделать: отложенные кадры из других условий, дособрать данные.
- **Симптом:** ложные срабатывания на тенях/бликах
  - Возможная причина: мало негативных примеров.
  - Что сделать: добавить «пустые» кадры с тенями в обучение, временная фильтрация.
- **Симптом:** после INT8 точность упала сильно
  - Возможная причина: плохая калибровка квантования.
  - Что сделать: калибровочный набор из своих данных, FP16 как компромисс.
- **Симптом:** ID объекта скачет
  - Возможная причина: нет трекера или слабое сопоставление.
  - Что сделать: ByteTrack, детекция каждый кадр для тестов.
