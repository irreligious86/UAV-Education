Computer vision: from OpenCV to neural networks

L4 — Expertreading 45 minstudy ~5 hArduPilot · PX4MASTERED

Детектор на борту — это не «запустить YOLO», а выбор между классическими методами (цвет, контуры, маркеры — дёшево, предсказуемо, хрупко) и нейросетью (устойчиво, дорого, нужно ускорение), затем измерение: FPS на целевом железе, точность (precision/recall/mAP) на своих данных, ложные срабатывания и их цена в контуре управления. Модуль проходит обе ветки с кодом, показывает запуск модели на Jetson (TensorRT) и Pi (NCNN/ONNX Runtime/Coral), и учит оценивать результат честно.

After this module you can
  • detect objects with classical methods and a YOLO-like model
  • run a model on a Jetson/Pi with acceleration
  • assess accuracy and false positives

Theory

Классика: когда её хватает

  • Маркеры (ArUco/AprilTag): известный объект с кодом → детекция + поза 6DoF с субпиксельной точностью, десятки FPS на Pi, устойчиво к освещению. Для точной посадки, калибровки, тестов контура — лучший выбор (ArduPilot precision landing умеет AprilTag через companion, PLND_TYPE = 1 MAVLink LANDING_TARGET).
  • Цвет + контуры: HSV-порог → морфология → findContours → фильтр по площади/форме. 2–5 мс на кадр. Ломается при смене освещения; калибровка порогов на месте.
  • Фон/движение: вычитание фона (createBackgroundSubtractorMOG2) — только для неподвижной камеры; с дрона — оптический поток и компенсация движения, сложно.
  • Шаблоны/признаки (ORB + сопоставление): для известного объекта; хрупко к масштабу и повороту.

Нейросети: детекция

Однопроходные детекторы (семейство YOLO, SSD, NanoDet) — вход 320–640 px, выход — боксы с классом и уверенностью, затем NMS. Факты для борта:

  • Размер модели: nano/small (2–10 млн параметров) — единственный реальный вариант на Pi/Jetson Nano/Orin Nano; medium — Orin NX/AGX.
  • Ускорение: Jetson — экспорт в TensorRT (FP16/INT8, ×3–10 к PyTorch); Pi 4/5 — NCNN или ONNX Runtime на CPU (nano-модель 320 px: 5–15 fps на Pi 5), Coral USB (INT8-модели) или Hailo-8L (Pi AI Kit, 13 TOPS) или Hailo-8 (AI HAT+ 26 TOPS) — десятки fps; ARM-ноутбуки/мини-ПК с GPU — любой стек.
  • Дообучение на своих данных обязательно: предобученная на COCO модель «видит» людей и машины, но не твой маркер/объект. 300–1000 размеченных кадров с борта (разные высоты, освещение, фон), аугментации, 50–100 эпох на ПК/Colab; экспорт в ONNX → TensorRT/NCNN.
  • Квантование INT8 — ×2 по скорости, −1–3% mAP; калибровочный набор из своих данных.

Метрики, которые имеют смысл

  • Precision = TP/(TP+FP) — доля правильных среди найденных; Recall = TP/(TP+FN) — доля найденных среди истинных; порог уверенности двигает одно за счёт другого (PR-кривая).
  • mAP@0.5 — площадь под PR при IoU ≥ 0.5; стандарт, но для борта важнее: recall при фиксированной precision (цена FP — ложный манёвр!) и задержка полного цикла (захват → инференс → NMS → команда).
  • Оценивать на отложенных кадрах с борта, не на обучающих; отдельно по условиям (высота, освещение) — модель «в среднем 0.9» может давать 0.5 на закате.
  • FP анализ: классифицировать ложные срабатывания (похожий объект, тень, край кадра, блик) — каждая группа лечится по-своему: данные, порог, геометрический фильтр (размер объекта по высоте полёта), временная фильтрация (объект должен появиться в N кадрах подряд — трекер).

Разобранный пример: метрики из счётчиков

Отложенный набор: 200 кадров, на них 250 объектов. Детектор при пороге уверенности 0.5 выдал 230 рамок: 210 совпали с разметкой по IoU ≥ 0.5 (TP), 20 — ложные (FP), 40 объектов пропущено (FN).

  • Precision = TP / (TP + FP) = 210/230 = 0.91 — из того, что нашли, 91 % правда.
  • Recall = TP / (TP + FN) = 210/250 = 0.84 — из того, что было, нашли 84 %.
  • IoU = площадь пересечения / площадь объединения рамок; 0.5 — «совпало», 0.75 — «совпало точно».

Порог 0.3 даёт, скажем, precision 0.80 и recall 0.93; порог 0.7 — 0.96 и 0.70. Какой выбрать — решает цена ошибки, а не красота числа: в поиске человека пропуск дороже ложной тревоги (порог ниже, ложные тревоги проверяет оператор), в автоматическом действии по цели наоборот (порог выше плюс подтверждение несколькими кадрами).

Трекер поверх детектора

Детектор на каждом кадре — шумный и дорогой. Трекер (SORT/ByteTrack: Kalman + сопоставление по IoU) даёт стабильные ID, сглаживает, переживает пропуски и позволяет детектировать на каждом 2–3-м кадре. Для контура управления команды берутся от трекера, не от сырого детектора.

Пайплайн на борту

Захват (поток, последний кадр) → препроцессинг (resize, letterbox, нормализация — на GPU/аппаратно, где возможно) → инференс → NMS → трекер → публикация (ROS 2 топик / MAVLink / ZeroMQ) с timestamp кадра. Профилировать каждую стадию (time.perf_counter); типичные пропорции на Jetson Orin Nano для YOLO-nano 640: захват 3 мс, препроцесс 2, инференс TensorRT FP16 8–12, постпроцесс 2 → 15–20 мс, 50 fps теоретически, 30 с запасом.

Practice

Шаг 1. Классика

ArUco — детекция маркера с камеры, вывод id и углов, FPS. С OpenCV 4.7 API другой (старые cv2.aruco.detectMarkers из статей не работают):

import cv2, time
dictionary = cv2.aruco.getPredefinedDictionary(cv2.aruco.DICT_4X4_50)
detector = cv2.aruco.ArucoDetector(dictionary, cv2.aruco.DetectorParameters())
cap = cv2.VideoCapture(0)
t0, n = time.perf_counter(), 0
while n < 300:
    ok, frame = cap.read()
    if not ok:
        break
    corners, ids, _ = detector.detectMarkers(cv2.cvtColor(frame, cv2.COLOR_BGR2GRAY))
    if ids is not None:
        c = corners[0][0]
        print(ids.ravel()[0], "centre px:", c.mean(axis=0).round(1))
    n += 1
print(f"{n / (time.perf_counter() - t0):.1f} FPS")

HSV-детектор цветного объекта: пороги подобраны по гистограмме, площадь/форма фильтруют; FPS и ложные срабатывания при смене света.

Шаг 2. Данные и дообучение

Снять 300+ кадров с борта/с руки объекта в разных условиях; разметить (CVAT/LabelImg/Roboflow); обучить nano-модель (Ultralytics/NanoDet) на ПК; экспорт ONNX. Отложенный набор — 20%.

Шаг 3. На борту

Jetson: ONNX → TensorRT FP16 (trtexec), инференс в Python; Pi: NCNN/ONNX Runtime или Coral/Hailo. Профиль по стадиям, FPS с камерой (не с файла!).

Шаг 4. Оценка

Precision/recall/mAP на отложенном наборе, по условиям; кривая precision–recall по 5 порогам и выбранный порог с обоснованием ценой ошибки (как в разобранном примере); FP классифицированы; трекер поверх (ByteTrack/SORT) — стабильность ID на видео.

Как считать и что записать

  • FPS — с камерой, а не с файла: захват, предобработка и инференс вместе. Профиль по стадиям (мс на кадр) покажет, где узкое место. Часто это не нейросеть, а копирование кадра и изменение размера.
  • Precision и recall на отложенном наборе. Пример: в отложенных кадрах 100 объектов, детектор нашёл 90 из них и ещё 10 раз сработал на пустом месте. Precision = 90 / (90 + 10) = 0.90, recall = 90 / 100 = 0.90. Повышение порога уверенности обычно поднимает precision и снижает recall.
  • Выбор порога через цену ошибки. Если ложное срабатывание уводит аппарат за чужой целью, а пропуск означает только повторный заход, выбирай порог с высокой precision, даже ценой recall. Запиши кривую по 5 порогам и выбранную точку с одной фразой обоснования.
  • Ложные срабатывания по классам: блики, тени, похожие объекты, размытие движения. Для каждого класса — пример кадра и мера: данные в обучение, фильтр по размеру или форме, трекер с подтверждением по нескольким кадрам.
  • ArUco: id маркера и углы стабильны при неподвижной камере. Если углы «прыгают», маркер мал в кадре или камера не откалибрована (модуль «Камера»).

Лабораторная засчитывается, когда модель запущена на борту с FPS, измеренным с камерой по стадиям, precision/recall посчитаны на отложенном наборе с выбранным порогом и обоснованием, а ложные срабатывания классифицированы с мерой для каждого класса.

Troubleshooting

Симптом: 30 fps на файле, 8 fps с камеры

  • Возможная причина: захват/конверсия на CPU, копии кадра.
  • Что сделать: профиль стадий, аппаратный препроцесс, нижнее разрешение.

Симптом: mAP 0.9 на валидации, в поле — не видит

  • Возможная причина: валидация из того же распределения, что обучение; поле другое.
  • Что сделать: отложенные кадры из других условий, дособрать данные.

Симптом: ложные срабатывания на тенях/бликах

  • Возможная причина: мало негативных примеров.
  • Что сделать: добавить «пустые» кадры с тенями в обучение, временная фильтрация.

Симптом: после INT8 точность упала сильно

  • Возможная причина: плохая калибровка квантования.
  • Что сделать: калибровочный набор из своих данных, FP16 как компромисс.

Симптом: ID объекта скачет

  • Возможная причина: нет трекера или слабое сопоставление.
  • Что сделать: ByteTrack, детекция каждый кадр для тестов.
