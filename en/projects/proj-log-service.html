Log analysis service

Project 3L3~25 hhas a starterPASSED

A report with findings from a flight log: vibration and clipping, battery sag and internal resistance, errors, GPS, attitude tracking error. Every finding has a threshold and an explanation; the report is a single HTML file.

Stack

  • Python, pymavlink
  • blackbox_decode (Betaflight)
  • matplotlib → встроенные SVG/PNG
  • pytest на синтетических логах

Starter: examples/log-report — clone it and start with its README.

Can replace the capstone project of track “Integrator”.

Stages

  1. DataFlash analysis: VIBE, BAT, ERR, GPS, ATT, MODE, MSG
    Verification: pytest examples/log-report/tests -k "clean_flight or vibration or battery"
  2. Checks with thresholds and severity, JSON output
    Verification: pytest examples/log-report/tests -k err_and_gps
  3. HTML report with plots and a flight-mode timeline
    Verification: pytest examples/log-report/tests -k cli_writes
  4. Betaflight Blackbox input via blackbox_decode
    Verification: demo in the report
  5. EKF checks (XKF4) and regression tests on your own logs
    Verification: demo in the report

Acceptance criteria

The project is passed when all items are done. Check them off as you go:

Auto-check

pytest examples/log-report/tests (5 tests on synthetic logs)

Grading

Passed when all acceptance criteria are met. The quality level is judged by the criteria below; each level includes the previous one.

  • Functionality
    • Accepted: All stages work in the scenario from the README
    • Good: Plus failure scenarios: link loss, missing data, invalid input
    • Excellent: Plus at least one "excellent" assignment from the project list
  • Verifiability
    • Accepted: Starter tests pass, your own functions are covered by at least one test
    • Good: A test for each stage; tests run in CI
    • Excellent: Failure and regression tests on your own data; coverage of the key logic visible in the report
  • Engineering report
    • Accepted: The measurements required by the acceptance criteria are present
    • Good: Measurements with a method and repeatability (several runs, spread)
    • Excellent: A comparison of solution options with a conclusion, limitations and next steps
  • Code and documentation
    • Accepted: README: one-command launch, architecture
    • Good: Modules separated, interfaces documented, no unexplained "magic numbers"
    • Excellent: The code is readable without the author: docs/, examples, commit history by stage

“Excellent”-level tasks

  • Regression: 10 of your own logs with a known verdict, the service is never wrong
  • Comparing two "before/after" tuning logs in a single report

What to submit

  • Tool + README
  • Three reports on your own logs and a comparison with manual analysis

Required modules

  1. ArduPilot logs: flight analysis
  2. Blackbox
  3. Python for flight data analysis
  4. Troubleshooting tree: the drone won't take off
  5. ArduPilot tuning: AUTOTUNE, filters, ESC-based notch
Safety. Anything that controls the aircraft goes through tests and SITL first. Real flights only with a verified failsafe and a pilot ready to take over.
