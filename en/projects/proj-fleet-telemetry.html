Fleet telemetry to the cloud + dashboard

Project 2L3~35 hhas a starterPASSED

Each vehicle publishes compressed telemetry to MQTT through its companion; a service stores it in a time-series database, Grafana displays the fleet, and alerts fire on battery, link loss and EKF.

Stack

  • MQTT (Mosquitto)
  • Python-ingest
  • InfluxDB или TimescaleDB
  • Grafana
  • Docker Compose

Starter: examples/fleet-telemetry — clone it and start with its README.

Can replace the capstone project of track “Engineer: code on board”.

Stages

  1. Topic schema and message format (JSON/CBOR), version in every message
    Verification: pytest examples/fleet-telemetry/tests -k schema
  2. Publisher on the companion: 1–5 Hz, buffering while the network is down
    Verification: pytest examples/fleet-telemetry/tests -k "outage or overflow"
  3. Ingest into the database with schema validation and a vehicle tag
    Verification: pytest examples/fleet-telemetry/tests -k duplicates
  4. Fleet dashboard: map, battery, flight modes, link
    Verification: demo in the report
  5. Alerts: battery, no data for > 10 s, EKF failsafe
    Verification: pytest examples/fleet-telemetry/tests -k alerts

Grading

Passed when all acceptance criteria are met. The quality level is judged by the criteria below; each level includes the previous one.

  • Functionality
    • Accepted: All stages work in the scenario from the README
    • Good: Plus failure scenarios: link loss, missing data, invalid input
    • Excellent: Plus at least one "excellent" assignment from the project list
  • Verifiability
    • Accepted: Starter tests pass, your own functions are covered by at least one test
    • Good: A test for each stage; tests run in CI
    • Excellent: Failure and regression tests on your own data; coverage of the key logic visible in the report
  • Engineering report
    • Accepted: The measurements required by the acceptance criteria are present
    • Good: Measurements with a method and repeatability (several runs, spread)
    • Excellent: A comparison of solution options with a conclusion, limitations and next steps
  • Code and documentation
    • Accepted: README: one-command launch, architecture
    • Good: Modules separated, interfaces documented, no unexplained "magic numbers"
    • Excellent: The code is readable without the author: docs/, examples, commit history by stage

“Excellent”-level tasks

  • Deduplication and ordering survive 10 % duplicates and packet reordering
  • Traffic calculation per vehicle-hour and format choice (JSON vs CBOR) based on measurement

What to submit

  • docker-compose.yml, publisher, ingest, dashboard as JSON
  • Report: traffic, latency, behavior during outages

Required modules

  1. MAVLink routing and transport: radio, 4G, multiple GCSs
  2. Libraries on top of MAVLink: pymavlink, MAVSDK, MAVROS: what to use and when
  3. Raspberry Pi + ArduPilot
  4. Navigation and link resilience to interference
  5. Systems engineering: requirements, FMEA, documentation, tests
Safety. Anything that controls the aircraft goes through tests and SITL first. Real flights only with a verified failsafe and a pilot ready to take over.
