Web GCS: telemetry, map, flight modes

Project 1L3~30 hhas a starterPASSED

A ground control station in the browser: the backend reads MAVLink and serves telemetry over WebSocket; the frontend draws the vehicle on a map, shows the flight mode, battery and STATUSTEXT, and can arm and change modes with confirmation.

Stack

  • Python 3, pymavlink, asyncio
  • WebSocket (websockets)
  • JS, Leaflet, без фреймворка
  • ArduPilot SITL

Starter: examples/web-gcs — clone it and start with its README.

Can replace the capstone project of track “Engineer: code on board”.

Stages

  1. MAVLink → JSON bridge over WebSocket: HEARTBEAT, GLOBAL_POSITION_INT, ATTITUDE, SYS_STATUS, STATUSTEXT
    Verification: pytest examples/web-gcs/tests -k "frame or battery"
  2. A page with a map and a vehicle marker, mode and battery on a panel
    Verification: demo in the report
  3. Commands from the browser: arm/disarm and mode changes via COMMAND_LONG waiting for an ACK, response in the UI
    Verification: pytest examples/web-gcs/tests -k commands_are_acked
  4. Robustness: link loss detected within 3 s (heartbeat timeout), reconnection without a page reload
    Verification: pytest examples/web-gcs/tests -k link_loss
  5. Recording a session to a tlog and replaying it in the same UI
    Verification: demo in the report

Acceptance criteria

The project is passed when all items are done. Check them off as you go:

Auto-check

pytest examples/web-gcs/tests: parsing messages to JSON, commands with ACK, heartbeat timeout

Grading

Passed when all acceptance criteria are met. The quality level is judged by the criteria below; each level includes the previous one.

  • Functionality
    • Accepted: All stages work in the scenario from the README
    • Good: Plus failure scenarios: link loss, missing data, invalid input
    • Excellent: Plus at least one "excellent" assignment from the project list
  • Verifiability
    • Accepted: Starter tests pass, your own functions are covered by at least one test
    • Good: A test for each stage; tests run in CI
    • Excellent: Failure and regression tests on your own data; coverage of the key logic visible in the report
  • Engineering report
    • Accepted: The measurements required by the acceptance criteria are present
    • Good: Measurements with a method and repeatability (several runs, spread)
    • Excellent: A comparison of solution options with a conclusion, limitations and next steps
  • Code and documentation
    • Accepted: README: one-command launch, architecture
    • Good: Modules separated, interfaces documented, no unexplained "magic numbers"
    • Excellent: The code is readable without the author: docs/, examples, commit history by stage

“Excellent”-level tasks

  • Mission upload and editing on the map (MISSION_ITEM_INT) with read-back verification
  • Multiple vehicles in one UI by sysid

What to submit

  • Repository with backend/, web/, docs/protocol.md
  • Video or GIF: a mission flown in SITL in your UI
  • Report: latency measurement, what was done for stability

Required modules

  1. MAVLink internals: frame, CRC, dialects, signing
  2. MAVLink microservices: commands, parameters, missions, streams
  3. MAVLink routing and transport: radio, 4G, multiple GCSs
  4. Libraries on top of MAVLink: pymavlink, MAVSDK, MAVROS: what to use and when
  5. Raspberry Pi + ArduPilot
  6. SITL: a drone without a drone
Safety. Anything that controls the aircraft goes through tests and SITL first. Real flights only with a verified failsafe and a pilot ready to take over.
