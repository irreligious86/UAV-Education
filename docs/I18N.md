# Languages (i18n)

The course is written in Russian (the source language) and published in every language listed in
`i18n/languages.json`: Russian at the site root, every other language under `/<dir>/` with the same
structure (`/ua/m/f-power.html` is the Ukrainian page of `/m/f-power.html`; the URL and the picker say UA, while the language code stays the ISO 639 `uk` in `lang`/`hreflang` and in `i18n/uk/`. Former `/uk/` links redirect, see `oldDirs`). Nothing has to be translated
for a language to build: anything without a translation is shown in the source language, and untranslated
modules say so.

## What the visitor gets

- A language picker in the header (`RU · UA · EN · GAL`) on every page; it opens the same page in that language.
- The choice is remembered (`localStorage["uav-lang"]`). An early script in `<head>` sends every later
  page — the home page, old links, bookmarks — to the chosen language before anything paints. A shared
  link opens as sent until the visitor picks a language themselves. `?lang=keep` disables the redirect.
- Signed in (accounts on): the language is stored in the account (`profiles.lang`,
  `supabase/migrations/0005_profile_language.sql`) and applied right after login on any device; the header
  picker and «Язык интерфейса» on the account page change it there. An account without a language takes
  the one in use at its first login.
- Progress, grades, exams and groups are shared across languages: a module passed in Ukrainian is passed.
- Every page carries `<link rel="alternate" hreflang>` for each language.

## Files

| What | Source | Translation |
|---|---|---|
| Interface (build, JS, diagrams) | Russian strings in `scripts/build_site.py` (`_()`, `tr_html()`), `assets/**/*.js` (`T()`), diagram generators | `i18n/<lang>/ui.json` |
| Data: tracks, objectives, labs, projects, formulas, glossary, manifest titles | `data/*.json` | `i18n/<lang>/data.json` |
| A module | `content/<track>/<id>.md` | `i18n/<lang>/content/<track>/<id>.md` |
| Quiz bank | `content/quiz/<id>.json` | `i18n/<lang>/content/quiz/<id>.json` |
| Numeric task bank | `content/tasks/<id>.json` | `i18n/<lang>/content/tasks/<id>.json` |
| Hand-written pages | `content/pages/<name>.html` | `i18n/<lang>/content/pages/<name>.html` |

Catalogs are gettext-style: the key is the Russian source string, the value its translation; an empty
value means "not translated yet". Keep `{placeholders}` and leading/trailing spaces exactly; HTML inside a
string (links, `<code>`) stays HTML.

## Translating

1. `python scripts/i18n_extract.py --todo` — refreshes the catalogs with every current key and writes
   `i18n/<lang>/todo-ui.json` / `todo-data.json` (only what is left; not committed).
2. Fill the values in `ui.json` / `data.json`.
3. A module: copy the source to `i18n/<lang>/content/...`, translate the prose and keep the structure —
   the same `## section` keys, the same `{{diagram:…}}` / `{{widget:…}}` lines (translate only the caption
   after `|`), the same code blocks (translate comments and output text only where it is prose, never
   parameter names, commands or values). Set `source_hash` in the front matter to the hash of the source
   file: `python -c "import sys; sys.path.insert(0,'scripts'); import i18n; print(i18n.source_hash(open('content/foundation/f-power.md').read()))"`.
   In diagnostics keep the field markers: `**Symptom:**` / `**Симптом:**`, and start the detail lines with
   the field name of your language (see `FIELD_KEYS` in `scripts/build_site.py`).
4. Quiz and task banks: the same file with translated text. A string parameter (e.g. `"s": ["без подписи", "с подписью"]`) keeps its source values; add `"labels": {"s": {"без подписи": "unsigned", ...}}` to the translated task so the statement shows them in your language. Answers, option count and order, parameters,
   formulas and tolerances must stay identical — `check_i18n.py` enforces it, grading depends on it.
5. `python scripts/publish.py`.

When the Russian source of a module changes, its translation is marked stale (the hash no longer matches)
and the page shows «the original was updated after the translation». Update the text and the hash.

Terminology: `i18n/<lang>/terms.md` is the glossary translators follow, so the same term reads the same in
every module.

## Checks

- `scripts/check_i18n.py` (in `publish.py` and CI): catalogs well-formed, placeholders and spacing match,
  translated modules keep the structure, quizzes and tasks grade the same; prints coverage per language.
- `scripts/check_links.py` and `scripts/check_rendering.py` walk every language tree.
- `tests/e2e/i18n.e2e.js`: picker, remembered choice, account language on a new device, fallback notice.
- The source language output of the build is unchanged by the i18n layer (checked when it was introduced).

## Dialects and regional variants (fallback chains)

A language may name a `fallback` in `i18n/languages.json`. Everything it does not translate itself — interface
strings, data, modules, quiz and task banks, diagrams — comes from the fallback before the source language:
`uk-galych → uk → ru`. So a dialect or a regional variant (`en-GB` over `en`) is usable from the first
commit and only needs the differences. `uk-galych` (Galician dialect of Ukrainian, `/gal/`) is the first
one: an experiment, written from the reviewed Ukrainian translation with the rules in
`i18n/uk-galych/terms.md` (dialect lives in the prose; technical terms, parameters and formulas stay standard).
Language codes are BCP 47 (`uk-galych` uses a variant subtag); account languages accept them (migration 0006).

## Adding a language

1. One entry in `i18n/languages.json` (`code`, `dir`, `name`, `short`, `htmlLang`, optional `fallback`, optional `oldDirs` when a URL directory is renamed).
2. `python scripts/i18n_extract.py` creates `i18n/<code>/ui.json` and `data.json`.
3. `python scripts/publish.py` builds `/<dir>/`; translate as above. Nothing else changes — CI reads the
   language directories from `scripts/i18n.py --dirs`.
