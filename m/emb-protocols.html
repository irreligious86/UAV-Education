UART, I2C, SPI, CAN на уровне сигналов и драйверов

Теория

UART

Асинхронный: нет тактовой линии, обе стороны знают скорость. Кадр: стартовый бит (0), 5–9 бит данных (LSB первым), опционально паритет, 1–2 стоповых (1). 8N1 на 115200 → 10 бит на байт → 11 520 байт/с. Приёмник сэмплирует в середине бита (обычно ×16 передискретизация); ошибка скорости до ~3–5% терпима, больше — framing error. Ошибки: framing (стоп-бит не 1 — неверная скорость/инверсия), overrun (не успели забрать байт — нужен DMA/прерывание), noise. Инверсия (SBUS): уровни перевёрнуты, idle = 0. Уровни 3.3 В TTL; RS-232/RS-485 — другие уровни/дифф. пара (длинные линии).

Драйвер: кольцевой буфер приёма по прерыванию/DMA, парсер кадров протокола (CRSF: [адрес][длина][тип][payload][CRC8 0xD5]; MAVLink: magic 0xFD, длина, seq, sysid/compid, msgid, CRC16 с CRC_EXTRA), таймаут между байтами для ресинхронизации.

I2C

Синхронный, две линии open-drain с подтяжками: SCL, SDA. Мастер генерирует такт; транзакция: START (SDA↓ при SCL=1) → 7-бит адрес + бит R/W → ACK от ведомого (SDA↓ на 9-м такте) → байты данных с ACK/NACK → STOP. Чтение регистра: START, адрес+W, номер регистра, повторный START, адрес+R, данные, NACK последнего, STOP. Скорости 100/400 кГц (fast), 1 МГц (fast-plus). Ограничения: ёмкость шины ≤ 400 пФ → провода до ~30–50 см, подтяжки 2.2–4.7 кОм (меньше — круче фронты, больше ток). Ошибки: NACK на адрес (нет устройства/адрес/питание), NACK на данные, зависшая шина (ведомый держит SDA=0 после сбоя мастера — лечится 9 тактами SCL вручную, «bus recovery»), clock stretching (ведомый тянет SCL — мастер должен уметь ждать; у некоторых МК/датчиков проблемы).

SPI

Синхронный, полный дуплекс: SCLK, MOSI, MISO, CS (по линии на устройство). Нет адресов и ACK: мастер опускает CS, выдаёт такты, каждый такт сдвигает бит в обе стороны. Режимы CPOL/CPHA (0–3) — полярность/фаза такта, должны совпадать с даташитом (ICM42688 — mode 0 или 3). Скорости до десятков МГц (гироскоп 8–24 МГц, flash 50+). Чтение регистра: байт адреса с битом R (часто старший бит = 1), затем N байт мусора на MOSI — данные на MISO. Burst-чтение 14 байт IMU за одну транзакцию — так делают все прошивки. Ошибок «протокола» нет — проверка целостности только по смыслу (WHO_AM_I регистр, значения в диапазоне). Короткие дорожки: SPI наружу платы почти не выводят.

CAN и DroneCAN

CAN 2.0: дифференциальная пара CAN_H/CAN_L, терминаторы 120 Ом с обоих концов, до 1 Мбит/с (до 40 м при 1 Мбит, дольше — медленнее). Кадр: идентификатор 11 или 29 бит (расширенный), DLC, до 8 байт данных, CRC15, ACK от любого приёмника. Арбитраж: все передают одновременно, доминантный 0 побеждает рецессивную 1 — меньший ID выигрывает без потери времени; приоритет заложен в ID. Контроллер CAN в МК принимает/отправляет кадры аппаратно, фильтрует по ID; ошибки считаются (error passive/bus-off при 256 ошибках — узел отключается).

DroneCAN (бывший UAVCAN v0): поверх CAN — 29-битный ID с приоритетом, типом сообщения и node ID источника (1–127), многокадровые сообщения с транспортным CRC и toggle-битом, динамическое распределение node ID (DNA), стандартные типы: uavcan.equipment.gnss.Fix2, ahrs.MagneticFieldStrength2, esc.RawCommand/Status, power.BatteryInfo, range_sensor.Measurement. Зачем на больших аппаратах: одна витая пара на все устройства, помехоустойчивость дифф. пары и CRC, телеметрия от каждого ESC, горячая замена узлов, длинные линии (крыло 2 м), без «один UART — одно устройство». Инструмент: DroneCAN GUI Tool (SLCAN-адаптер или полётник как мост CAN_SLCAN_CPORT) — видно узлы, параметры узлов, сообщения.

Драйвер: что должно быть

  1. Инициализация шины и проверка устройства (WHO_AM_I/chip id).
  2. Конфигурация (регистры): диапазон, частота, фильтры.
  3. Чтение блоком с таймаутом; возврат ошибки, не зависание.
  4. Преобразование сырых единиц в физические (LSB → °/с, Па).
  5. Обработка ошибок: счётчики, повторная инициализация после N ошибок подряд, bus recovery для I2C.
  6. Потокобезопасность: мьютекс на шину, если устройств несколько.

Практика

Шаг 1. Драйвер I2C-датчика (ESP32, ESP-IDF; пример на legacy-API driver/i2c.h, который объявлен end-of-life с ESP-IDF v6.0 — в новых проектах driver/i2c_master.h: i2c_master_transmit_receive/i2c_master_transmit)

Пример для BMP280 (адрес 0x76/0x77, chip id 0x58 в регистре 0xD0):

static esp_err_t rd(uint8_t reg, uint8_t *buf, size_t n) {       // repeated-START read, 50 ms timeout
  return i2c_master_write_read_device(I2C_NUM_0, ADDR, &reg, 1, buf, n, pdMS_TO_TICKS(50));
}
static esp_err_t wr(uint8_t reg, uint8_t val) {
  uint8_t b[2] = { reg, val };
  return i2c_master_write_to_device(I2C_NUM_0, ADDR, b, 2, pdMS_TO_TICKS(50));
}
esp_err_t bmp280_init(void) {
  uint8_t id; ESP_RETURN_ON_ERROR(rd(0xD0, &id, 1), TAG, "no response");
  if (id != 0x58) return ESP_ERR_NOT_FOUND;
  ESP_RETURN_ON_ERROR(rd(0x88, calib, 24), TAG, "calib");         // dig_T1..dig_P9
  return wr(0xF4, 0x57);                                            // osrs_t x2, osrs_p x16, normal mode
}
esp_err_t bmp280_read(float *temp_c, float *press_pa) {
  uint8_t d[6]; esp_err_t e = rd(0xF7, d, 6); if (e != ESP_OK) { errors++; return e; }
  int32_t adc_p = (d[0] << 12) | (d[1] << 4) | (d[2] >> 4), adc_t = (d[3] << 12) | (d[4] << 4) | (d[5] >> 4);
  /* compensation formulas from the datasheet (bmp280_compensate_T/P) */ ...
  return ESP_OK;
}

Читать 50 Гц, выводить; после 5 ошибок подряд — переинициализация с логом.

Шаг 2. Анализатор

Снять транзакцию: START, адрес+W, 0xF7, повторный START, адрес+R, 6 байт, NACK, STOP. Сопоставить байты с выводом. Записать длительность транзакции при 400 кГц (ожидаемо ~0.2 мс).

Шаг 3. Сломать шину

Отключить SDA на ходу → NACK/таймаут, счётчик ошибок, переинициализация; замкнуть SDA на землю на секунду → зависшая шина; реализовать recovery (9 тактов SCL в GPIO-режиме) и показать восстановление.

Шаг 4. DroneCAN (если есть узел)

DroneCAN GUI Tool через SLCAN-мост полётника: увидеть node ID, GetNodeInfo, сообщения GPS/компаса; снять кадр CAN анализатором и разобрать 29-битный ID на приоритет/тип/источник.

Что должно получиться и что записать

  • Чтение датчика. Регистр 0xD0 BMP280 возвращает chip id 0x58 — первая проверка, что драйвер говорит с тем устройством. Если приходит 0x60, это BME280 (у него есть и влажность). Давление и температура после компенсации по калибровочным коэффициентам — правдоподобные: около 1000 гПа и комнатная температура. Подними плату на метр — давление упадёт примерно на 0.12 гПа.
  • Длительность транзакции. Чтение 6 байт с повторным стартом на 400 кГц — около 85 тактов шины (адреса, регистр, данные, ACK) × 2.5 мкс ≈ 0.21 мс. Сравни с анализатором: заметно дольше — значит, драйвер делает паузы между байтами или на линии слабые подтяжки (пологие фронты).
  • Ошибки. Отключённая SDA даёт NACK или таймаут, счётчик ошибок растёт, после пяти подряд — переинициализация с записью в лог. SDA, прижатая к земле, вешает шину. Девять тактов SCL в режиме GPIO освобождают ведомое устройство, и чтение возобновляется. Запиши время от сбоя до восстановления.
  • CAN. 29-битный ID кадра DroneCAN разобран на приоритет, тип сообщения и номер узла-отправителя, и номер совпадает с тем, что показывает DroneCAN GUI Tool.

Лабораторная засчитывается, когда I²C-датчик прочитан своим драйвером с проверкой chip id, шина снята анализатором с длительностью транзакции, а ошибка на шине воспроизведена и обработана с восстановлением.

Диагностика

Симптом: UART принимает мусор

  • Возможная причина: скорость/инверсия/нет общей земли; overrun без DMA.
  • Что сделать: проверить анализатором, DMA-приём, framing/overrun счётчики.

Симптом: I2C-транзакция «висит»

  • Возможная причина: ведомый держит SDA; clock stretching без поддержки.
  • Что сделать: таймауты в драйвере, bus recovery, снизить до 100 кГц.

Симптом: SPI возвращает 0xFF/0x00

  • Возможная причина: CS не опускается, режим CPOL/CPHA, слишком быстро.
  • Что сделать: осциллограф на CS/SCLK, режим по даташиту, WHO_AM_I тест.

Симптом: CAN-узел уходит в bus-off

  • Возможная причина: нет терминаторов, разная скорость, перепутаны H/L.
  • Что сделать: 120 Ом с обоих концов, одна скорость, счётчики ошибок.

Симптом: датчик работает на столе, но не на борту

  • Возможная причина: помехи на I2C от силовых, длина проводов.
  • Что сделать: короче/витые/экран, SPI или CAN вместо I2C.
