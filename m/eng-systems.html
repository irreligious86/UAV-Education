Этот модуль — тот же цикл в полный рост, для аппарата или системы, которую будет продолжать другой человек: как писать требования, которые можно проверить (с ID, критерием и методом), как вести трассировку до тестов, как делать FMEA на уровне системы с мерами и их проверкой, как строить план верификации (SITL → стенд → поле) и как документировать так, чтобы передача заняла час, а не месяц. Теория

Требования

Хорошее требование: однозначное, проверяемое, с источником. Структура: ID | формулировка | критерий приёмки | метод проверки (анализ/симуляция/стенд/полёт) | источник (задача, правило, стандарт) | приоритет.

  • Плохо: «Дрон должен долго летать». Хорошо: R-PWR-03 | Время висения с полезной нагрузкой 500 г не менее 25 мин при 20 °C | лог: ток висения, расчёт по ёмкости ≥ 25 мин; полёт: ≥ 25 мин до BATT_LOW | полёт | задача заказчика §2.
  • Классы: функциональные (что делает), производительности (сколько), ограничения (масса, бюджет, закон), безопасность (failsafe, зоны), интерфейсы (MAVLink, питание нагрузки), эксплуатация (замена АКБ ≤ 2 мин без инструмента).
  • Требования безопасности выводятся из FMEA и правил, не придумываются из головы.
  • Каждое требование имеет владельца и статус (черновик/утверждено/проверено/не выполнено).

Архитектура и интерфейсы

Схема системы: блоки (FC, companion, питание, RC, видео, нагрузка), интерфейсы между ними с протоколом, питанием, направлением (таблица интерфейсов — главный документ при интеграции), бюджеты: массы (с запасом 10%), мощности (по веткам, из модуля про питание), связи (бюджет линка), вычислений (CPU companion). Решения с альтернативами и причиной выбора (ADR — architecture decision record: контекст, варианты, решение, последствия) — чтобы через год не спорить заново.

FMEA на уровне системы

Отличие от модуля про failsafe: рассматриваются не только отказы в полёте, но и интеграционные (ошибка в прошивке после обновления, неверная сборка, человеческий фактор при подготовке), для каждого — мера (устранение, резервирование, обнаружение, процедура) и как мера проверена (ссылка на тест). RPN пересчитывается после мер. Таблица живёт и обновляется после каждого инцидента (разбор → новая строка/обновлённая мера).

Верификация и валидация

  • Верификация — «сделали правильно?»: каждое требование → тест с методом; план тестов по ступеням: анализ/расчёт → SITL → стенд (без пропов) → привязной/низкий полёт → полёт. Результат каждого теста — запись с датой, конфигом (тег!), логом, вердиктом.
  • Валидация — «сделали то?»: прогон реальной задачи с заказчиком/пользователем; часто выявляет требования, которых не было.
  • Матрица трассировки: требование ↔ тест ↔ результат. Пустые клетки — незакрытые требования; тесты без требований — лишние или требование забыто.
  • Регрессия: после любого изменения — набор обязательных тестов (SITL-автотест из модуля про CI + короткий полётный чек-лист).

Документация, которую можно передать

Минимальный пакет: 1. README — что это, для чего, состояние, как запустить за 15 минут. 2. Требования (таблица) и ADR. 3. Архитектура: схема, таблица интерфейсов, бюджеты. 4. Сборка: BOM с версиями, схема проводки, фото, моменты затяжки где важно. 5. Конфигурация: репозиторий конфигов с тегами (модуль про CI). 6. FMEA и failsafe-настройки с обоснованием. 7. План и журнал тестов, матрица трассировки. 8. Эксплуатация: чек-листы (пред/послеполётный), журнал полётов, процедуры (замена АКБ, калибровки, обновление прошивки с откатом). 9. Журнал изменений и известные проблемы. Критерий качества: другой инженер по пакету восстанавливает аппарат и выполняет полёт без вопросов автору. Тест этого — попросить кого-то попробовать.

Процесс изменений

Запрос → оценка влияния на требования/FMEA → изменение в ветке → тесты (регрессия) → ревью → релиз с тегом → обновление документации в том же PR. Документация, обновляемая «потом», не обновляется никогда.

Практика

Шаг 1. Требования

20–40 требований для своего аппарата по структуре; ≥ 5 по безопасности из FMEA; каждое с методом проверки.

Шаг 2. Архитектура

Схема блоков, таблица интерфейсов, бюджеты массы/мощности/связи, 3 ADR (например: Li-Ion vs LiPo; ELRS 900 vs 2.4; companion Pi vs Jetson).

Шаг 3. FMEA и план тестов

Системная FMEA (≥ 15 строк) с мерами и ссылками на тесты; план тестов по ступеням; матрица трассировки.

Шаг 4. Пакет и передача

Собрать пакет (п. 1–9), дать прочитать другому человеку (или себе через неделю) с задачей «подготовь к полёту по документации» — список вопросов, которые возникли, → исправления. Лабораторная: требования с ID и трассировкой, FMEA, README и журнал изменений.

Диагностика

Симптом: требования есть, но тесты «по ощущениям»

  • Возможная причина: критерии приёмки не числовые.
  • Что сделать: переписать с числами и методом; требование без метода — не требование.

Симптом: после обновления прошивки всё сломалось

  • Возможная причина: нет регрессии и отката.
  • Что сделать: тег перед обновлением, регрессионный набор, процедура отката в документации.

Симптом: передача проекта заняла недели

  • Возможная причина: знания в голове, не в пакете.
  • Что сделать: тест передачи, ADR, таблица интерфейсов.

Симптом: FMEA написана один раз и устарела

  • Возможная причина: нет процесса обновления после инцидентов.
  • Что сделать: разбор инцидента завершается строкой в FMEA и изменением меры.
