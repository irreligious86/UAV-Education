INAV Programming Framework

L3 — Специалистчтение 25 минучёба ~3 чINAV 7.0+ОСВОЕН

INAV Programming Framework (IPF) — способ добавить аппарату логику без Lua и без companion: «если дальше 100 м — поднять мощность VTX», «если напряжение ниже порога — включить RTH», «переключить канал по условию». Логические условия выполняются прямо в прошивке, работают с телеметрией, режимами, точками миссии и глобальными переменными. Модуль объясняет модель (условие = операция + два операнда), синтаксис CLI, GVAR и типичные применения, включая сравнение с Lua в ArduPilot.

После модуля ты умеешь
  • собрать логическое правило с активатором
  • использовать GVAR как состояние

Теория

Модель

  • Logic Condition — одна строка «кода»: операция над одним-двумя операндами, с результатом true/false или числом.
  • Операнд — число, канал RC, параметр полёта (расстояние до дома, напряжение, высота, скорость), режим, другое условие, GVAR, точка миссии.
  • Активатор — другое условие, которое должно быть true, чтобы это выполнилось (−1 — всегда).
  • GVAR — глобальные переменные, целые; по умолчанию границы −32768…32767, командой gvar <i> <default> <min> <max> их можно расширить (хранятся как int32); их можно читать, писать, увеличивать и использовать в миксере серв.
  • Programming PID — четыре настраиваемых регулятора, выход которых доступен как операнд.

Синтаксис CLI

logic <rule> <enabled> <activatorId> <operation> <opA type> <opA value> <opB type> <opB value> <flags>

Типы операндов: 0 — значение, 1 — RC-канал, 2 — параметр полёта, 3 — режим, 4 — логическое условие, 5 — GVAR, 6 — Programming PID, 7 — точки миссии. Операции: сравнения (равно, больше, меньше), логические (AND, OR, NOT), арифметика, Set/Increase/Decrease GVAR, Override Throttle Scale, Override RC Channel, Set VTX power и другие. В 9.0 в конец списков добавлены операции 55 (Set Gimbal Sensitivity) и 56 (Override Minimum Ground Speed) и операнды полёта 46–49 (минимальная путевая скорость, скорость и направление ветра, относительный угол ветра); старые номера не сдвинулись. В Configurator 9 есть ещё вкладка JavaScript Programming (помечена как бета): код на JavaScript транспилируется в те же логические условия, так что ограничения остаются прежними.

Номера 9.1.0: как собрать строку logic без конфигуратора

Номера взяты из programming/logic_condition.h 9.1.0. С 8.0.1 они не менялись: операции 0–54 и операнды полёта 0–45 стоят на тех же местах, 9.x только дописал новые в конец. Порядок работы такой:

  1. Вход — фраза-правило: «если <величина> <сравнение> <порог>, то <действие>».
  2. Решение — для величины выбираешь тип операнда (таблица 1) и номер внутри типа (таблицы 2–4). Порог пересчитываешь в единицы операнда: 3.5 В на элемент → 350, 30 м высоты → 3000 см. Сравнение или действие — номер операции (таблица 5).
  3. Проверка — вводишь строку в CLI, команда logic без аргументов печатает правило обратно, а вкладка Programming показывает его живое значение. Если значение не похоже на величину (высота 12 при 12 м полёта), значит, перепутаны единицы или тип операнда.

Последнее поле строки logic — флаги: 0 — обычное правило, 1 — защёлка (latch): раз ставшее true правило больше не пересчитывается и остаётся true до следующего арма или дизарма, когда прошивка сбрасывает состояния всех правил (fc_core.c). Исключение — активатор: пока он false (и пока открыт CLI), значение правила 0, а пересчёт не возобновится до сброса, так что защёлку вешай на правило без активатора (−1). Защёлка, которую надо снимать тумблером в полёте, — операция STICKY, а не флаг.

Programming PID: команда pid

Регулятор нужен, когда правило должно не включать что-то, а держать величину: например, газ по высоте для привязного аэростата-шарика или угол сервы по крену. Формат 9.1.0 (fc/cli.c):

pid <№ 0–3> <вкл> <тип уставки> <уставка> <тип измерения> <измерение> <P> <I> <D> <FF>

Уставка и измерение — такие же операнды, как в logic (таблица 1). Коэффициенты — целые 0–32767, прошивка делит их на 1000: P = 500 значит 0.5. Выход ограничен −1000…1000 и читается другими правилами как операнд типа 6. Процедура: сначала P (I = D = 0), выход смотришь на вкладке Programming и проверяешь знак — при измерении ниже уставки выход должен расти; потом выход через Map Output (операция 37) переводишь в нужный диапазон; Map Output берёт A только в пределах 0…1000, отрицательная половина выхода PID обрезается до 0 — если она нужна, сначала прибавь 1000 и раздели на 2 (операции 14 и 17) и подаёшь в Override RC Channel или Override Throttle. Знак неверный — поменяй местами уставку и измерение, отрицательных коэффициентов команда не принимает.

Свои элементы OSD и JavaScript

Значение GVAR или результат правила выводится на экран через osd_custom_elements: до восьми элементов, каждый из трёх частей (текст, значение и др.), видимость всегда, по GVAR или по правилу. Формат и разобранный пример — в inav-osd-hd, здесь не повторяются. Тот же пример с VTX на вкладке JavaScript Programming (Configurator 9.x) пишется одной строкой: if (inav.flight.homeDistance > 100) { inav.override.vtx.power = 3; }. Транспилятор превращает её в те же два правила logic: после сохранения сверь их в CLI с шагом 2 практики.

Пример из документации: мощность VTX по удалению

Условие 0: «расстояние до дома > 100 м». Условие 1 (активатор 0): «установить мощность VTX = 3». Два правила — и передатчик сам поднимает мощность, когда аппарат далеко.

Где IPF уместен

  • автоматика на борту без второго компьютера: VTX, пин LED (операция 52), PINIO — не напрямую, а через подмену канала режима USER (операция 38, inav-led-pinio-beeper), сервы;
  • условные действия в миссии через user actions;
  • защиты: переключение режима по напряжению или удалению;
  • приборные задачи: GVAR как счётчики и состояния.

Против Lua в ArduPilot

Lua — полноценный язык с доступом к API автопилота, но требует F7/H7 и памяти. IPF — набор правил без циклов и функций, зато работает на F4 и настраивается из конфигуратора. Сложная логика в IPF быстро становится нечитаемой; граница — десяток-два правил.

Разобранный пример: защита по напряжению и удалению

Задача: при напряжении < 3.5 В/эл. и расстоянии > 300 м включить RTH и поднять мощность VTX. Правила (logic <rule> <enabled> <activator> <op> <A type> <A> <B type> <B> <flags>):

  • 0: cell voltage < 350 (операнд полёта «средн. напряжение элемента, сотые вольта» против значения 350) — результат true/false;
  • 1: distance to home > 300 (метры);
  • 2: AND с операндами «логическое условие 0» и «логическое условие 1» (тип операнда 4), без активатора → true, когда оба;
  • 3 (активатор 2): Override RC channel → канал режима RTH в положение «вкл» (RTH через переопределение канала);
  • 4 (активатор 1): Set VTX power = 3.

Проверка на столе без пропов: имитировать напряжение (АКБ разряженная/регулируемый БП) и расстояние (GVAR вместо реального операнда на этапе теста), смотреть статус правил на вкладке Programming конфигуратора. Правило-защита живёт в прошивке, значит, её логику надо документировать в паспорте аппарата: через месяц «сам включился RTH» будет загадкой.

Время и состояние: EDGE, STICKY, DELAY, TIMER, DELTA

Правила без памяти дают «дребезг»: напряжение под нагрузкой на секунду падает ниже порога — и RTH включается от одного рывка газа. Для этого в IPF есть операции со временем и памятью:

  • DELAY — true, только если условие A держится непрерывно N мс. Защита по напряжению — всегда через DELAY (например, 3000 мс), иначе защита сработает от просадки на панче.
  • STICKY — защёлка: включается по A и держится, пока не придёт B (сброс). «Один раз сработало — RTH, пока пилот не сбросит тумблером».
  • EDGE — true на N мс по фронту A: одно событие от удержания тумблера.
  • TIMER — периодически true/false: мигание света, пульсация зуммера.
  • DELTA — изменение значения за короткий интервал больше порога: «резкий спад высоты».

Переписанная защита: правило 0 → DELAY(3000) поверх «напряжение < 350», затем STICKY с установкой по AND(0, 1) и сбросом по тумблеру — и только её результат активирует переопределение канала.

Отладка

  • Вкладка Programming показывает состояние и значение каждого правила вживую — это главный отладчик.
  • GVAR можно вывести в OSD (элементы GVAR 0–3): видно состояние автомата в полёте и на записи видео.
  • logic и gvar в CLI печатают текущие правила — их дамп входит в diff all, то есть в резервную копию и в git (модуль «CI и версионирование конфигов»).

Ограничения, о которых спотыкаются

Правила выполняются в фиксированном порядке на частоте ~10 Гц; нет циклов, функций, строк; GVAR — целые; переопределение канала (Override RC) конфликтует с реальным стиком — для режимов лучше отдельный «виртуальный» канал. Число правил фиксировано прошивкой: 64 логических условия, 8 GVAR, 4 Programming PID — одинаково на F4 и H7. Если логика требует «состояний» и истории — это уже companion.

Место в системе

  • Получает: операнды из прошивки: напряжение элемента, расстояние до дома, высоту, режимы, RC-каналы, точки миссии (inav-gps, inav-missions); откалиброванное напряжение батареи (inav-setup-scratch).
  • Отдаёт: действия: переопределение RC-канала (например, включение RTH), мощность VTX (link-vtx), GVAR в OSD и в миксер серв; правила logic и gvar — в diff all и git (eng-ci-configs).
  • Если ошибиться здесь: защита по напряжению без DELAY → просадка на резком газе на секунду опускает напряжение ниже порога, и RTH включается сам посреди полёта; причину потом ищут в failsafe (inav-setup-scratch), а не в правилах. Override RC на канале, которым управляет пилот, → правило конфликтует с реальным стиком; для режимов нужен отдельный «виртуальный» канал.

Практика

Шаг 1. Первая пара правил в конфигураторе

Вкладка Programming: правило 0 — Flight > Home distance (m) больше 100; правило 1 — активатор 0, операция Set VTX Power, значение 3. Сохранить, проверить вкладку: состояние условий показывается вживую.

Шаг 2. То же в CLI

logic 0 1 -1 2 2 1 0 100 0
logic 1 1 0 25 0 3 0 0 0
save

Формат: logic <правило> <вкл> <активатор> <операция> <тип A> <значение A> <тип B> <значение B> <флаги>. Здесь операция 2 — GREATER_THAN, 25 — SET_VTX_POWER_LEVEL, операнд полёта 1 — расстояние до дома (м). Номера сверены с programming/logic_condition.h 9.1.0; в 8.0.1 они те же (в 9.0 новые операции и операнды только добавлены в конец). На другой версии перед вставкой сверяйся с документацией Programming Framework этой версии.

Шаг 3. GVAR как состояние

Правило: по срабатыванию тумблера увеличить GVAR 1 на 1; другое правило — если GVAR 1 чётная, включить свет, иначе выключить. Это конечный автомат на двух строках.

Шаг 4. Таблица истинности до полёта

Для защиты из разобранного примера выписать все комбинации входов и ожидаемый выход, затем проверить каждую строку на столе (без пропов), подменяя реальные операнды на GVAR, которые меняются тумблером:

Лабораторная

Собрать защиту: если напряжение ниже порога дольше 3 с (DELAY) и расстояние больше 50 м — защёлкнуть (STICKY) и переопределить канал режима в положение RTH (Override RC Channel). Пройти таблицу истинности на столе, проверить в SITL INAV, затем в поле на малом удалении. Сохранить в своём репозитории: дамп logic/gvar, заполненную таблицу, видео OSD с GVAR-состоянием. Работа выполнена, когда все пять строк таблицы истинности на столе дали ожидаемый выход (с порогом 50 м вместо 300 м), а вкладка Programming показывает те же состояния правил, что записаны в таблице.

Эталон для самопроверки. Правильная сборка: DELAY(3000) поверх «напряжение < порога», AND с расстоянием, STICKY с установкой по AND и сбросом по тумблеру — и только результат защёлки активирует Override RC Channel. RTH включается от короткой просадки на резком газе — защита собрана без DELAY. RTH выключается сам, как только напряжение восстановилось (пятая строка таблицы не проходит), — нет STICKY, переопределение висит прямо на AND. Правило не срабатывает совсем — активатор false или перепутан тип операнда (значение 1 вместо GVAR 1): смотри живое состояние на вкладке Programming.

Диагностика

Симптом: правило не срабатывает

  • Возможная причина: активатор false, неверный тип операнда (GVAR «значение 1» против «GVAR 1»).
  • Что сделать: смотреть живое состояние во вкладке Programming, проверить типы.

Симптом: Set GVAR пишет не в ту переменную

  • Возможная причина: в операнде A указан «Global Variable 1» вместо «Value 1».
  • Что сделать: индекс GVAR задаётся как Value.

Симптом: после обновления INAV правила сломались

  • Возможная причина: изменились номера операций/операндов (между 8.0.1 и 9.1.0 — нет: новые добавлены в конец).
  • Что сделать: сверить с таблицами версии, пересобрать правила.

Симптом: логика стала нечитаемой

  • Возможная причина: слишком много правил для IPF.
  • Что сделать: упростить или перейти на Lua/ArduPilot.
